# Awesome JEV directory UI

This document owns the directory's product-specific composition and behavior. Apply the stable visual tokens and review rules in [design.md](design.md); do not duplicate them here. The implementation lives in `src/App.tsx` and `src/components/*`.

## Reader and data

The current page helps readers find curated TypeSafe Jev / System One GitHub projects, judge their recorded summary and metadata, and inspect the original repository. It reads [`data/github.json`](../data/github.json). A distinct Jev news view reads [`data/news.json`](../data/news.json); X and YouTube records remain stored but hidden. Keep UI chrome localized in `src/i18n/locales/*` and retain source titles and summaries in their original language.

The opening viewport should reveal identity, searchable inventory, active controls, and the start of results. Keep the result set dominant rather than placing a marketing masthead ahead of the reader's task.

## Page composition

- The full-width sticky header contains the site title and three equal-size icon controls: source-repository link, theme menu, and language menu. The title returns to all projects and the top of the page. It uses the attributed React Bits `DecryptedText` source and its `motion/react` dependency with `speed=100`, `maxIterations=10`, `sequential=true`, `useOriginalCharsOnly=false`, `revealDirection=start`, `animateOn=hover`, and `clickMode=once`. The component's own character pool and reveal state remain upstream-owned. `maxIterations=10` has no effect in sequential mode; `clickMode` is inert outside click mode. Only pointer entry starts the decrypt; pointer exit restores the complete title, and a later entry replays it. There is no automatic loop. Reduced-motion readers see a static title. An invisible label reserves the final width without layout shift; the animated text stays on one line and may overhang during scrambling rather than wrap and clip the final letters. Both menus mark the current choice. Theme offers System, Light, and Dark; System follows operating-system changes, and selecting it clears any saved override. An effective color change uses a brief native crossfade where supported, but skips motion when the reader requests reduced motion. The language menu lists English and 简体中文, and both explicit theme and language choices persist across reloads. The header has no routine bottom divider.
- Language is a route property, not a post-hydration visual correction. English keeps the original URL; Chinese uses `/zh` plus the same path. Switching languages loads the equivalent prerendered page and stores the explicit choice; an unprefixed first visit uses that choice or, if absent, the browser's primary language before body paint. Do not infer language from IP geography. Project cards, list rows, title links, category navigation, and masked previews remain within the selected language variant.
- The centered content frame contains a full-width ASCII wordmark, two-line tagline, and data-update time when build history supplies one. Never manufacture a timestamp. The wordmark fits by CSS container width from first paint rather than resizing after hydration.
- On wide desktops (1280px and up), navigation occupies a 216px left rail beside the main results. The shared page frame is 1160px at most: rail and frame widths change together, preserving the 32px gap and the result-card width. Labels stay on one line with counts in their own right-aligned space. The sticky rail scrolls independently on short viewports. Below that breakpoint the same navigation opens the existing shadcn/Base UI left Sheet, leaving the full content width to the cards. The Sheet is a restrained 288px navigation panel, not a page-width overlay: its 56px header repeats the site's `Awesome JEV` brand link at the same top-left position, with an aligned close action and an accessible Categories dialog title; the list scrolls independently below it. The wordmark, results, and footer share the wider frame's edges. Top 100 Starred, Jev news, and Saved stay as three fixed shortcuts above the divider. All projects begins the project category group below it; only the categories below that point follow a stable English-label alphabetical order, with Other last, shared by both language settings. Top 100 Starred shows the highest-starred projects in the whole catalog; its limit is already in the label, so no duplicate count appears on the right. The cutoff uses global star rank, not the current search or sort order. Saved sits directly below Jev news; its browser-local count alone uses a compact outlined badge, while other counts remain aligned text from their respective data stores.
  The menu rows share a compact width based on the longest localized label and its count, with a 208px floor so shorter translations do not make the selection surface collapse. Counts still form one right-aligned column; only the Saved badge sits immediately after its label.
- Main controls are an underline search field, Stars / Date / Name sort, and cards / list view. Search is GitHub-only; query and the selected shortcut or category filter the results, sort orders them, and view changes their presentation. The Stars button has no ambiguous inventory count. Preserve the query when no items match.
- The cards view places each consecutive group of cards left-to-right on one reading row, even when card heights differ. It keeps cards at natural height rather than stretching them; preserving strict rank/date order takes priority over filling every short-card gap. Narrow screens use a single column. Once desktop card heights and positions are measured, offscreen card content can be skipped without losing its measured space; the full directory remains in the DOM. Card boundaries use an inset ring: the desktop `content-visibility` optimization clips an outside ring to the card box, leaving only corner fragments. The list view is a ranked table-like list of rank, project, and stars, not an activity dashboard.
- The footer ends the directory with a brief source note. Keep the opening and closing of the page connected even when the filtered result set is short.

The news shortcut swaps the main result area, not the header or design system. It has local text search, source attribution, newest-first order, and an incremental “show more” control rather than rendering an unbounded archive at once. Unlike the compact GitHub grid, news uses full-width cards grouped by Shanghai calendar date with a time rail, source line, AIHOT score when present, title, complete API summary, complete optional original title, and complete optional selection reason. Do not truncate these scarce reading fields merely to equalize card heights. The layout borrows the reading order of AIHOT's timeline but retains our tokens and radii. A plain click opens our own accessible, dismissible summary dialog with the original-source and AIHOT reading links; modified clicks retain the AIHOT link fallback. News previews use a masked TanStack search entry: the public URL stays `/news`, but browser Back first closes the dialog and Forward reopens it. There is no redundant “View details” label on the card: the dialog supplies outbound actions, not a promised full article. The dialog does not claim to display the article body or media, because the official API does not expose those fields; see [news.md](news.md) for the source boundary.

Saved is a browser-local reading list, not a repository data source or an account. The one `SaveButton` component appears on project cards, list rows, news cards, and both previews. It uses Phosphor's single-chevron `BookmarkSimple` rather than a star, so GitHub stars retain their original meaning. The visible project title is an internal detail link with a stretched click area over the card; `SaveButton` sits separately in `CardAction`, never inside that link, so activating it must neither navigate nor open the preview. On project cards the button sits in `CardAction`, centered to the title row without contributing to its row height; its icon—not the invisible button box—aligns with the card's right content inset. `CardDescription` spans both grid columns and keeps the full card width. The rank badge replaces the redundant GitHub mark at the start of the title row. No title or header padding is added to simulate the button column. On news cards it aligns with the source row's right content edge without crowding source or score. List rows align it to the row's right content edge. Cards and rows use a visually compact 32px control with an invisible 40px pointer target; previews keep a 40px control beside Close. Visible focus, `aria-pressed`, and distinct add/remove labels make the state usable without relying on color alone.

The Saved view separates projects from news, then offers only populated categories from each source's existing taxonomy; it does not invent user folders or merge incompatible category systems. Its search acts on the selected source, and cards reuse the regular project/news components and preview behavior. The active source and each source's category live in validated `/saved` search params, so leaving this view and using browser Back restores the same subfilter. Returning from either preview preserves that state; a news preview adds one masked history entry while hiding only its transient `preview` param from the public `/saved` URL. Browser storage contains only source-namespaced IDs and save times, never copies of titles or summaries; current catalog data owns display. Missing catalog IDs appear as removable unavailable entries rather than showing stale copied content. Storage denial leaves the displayed state unchanged and shows an error; updates in another tab refresh this view. Clearing browser data or switching devices loses these bookmarks. No key, analytics, server sync, or Action write is involved.

## Card ordering algorithm

`CardMasonry` receives items **after** search, filter, and sort. It must not change that sequence. On a desktop-sized grid, the column count comes from the CSS breakpoint (two or three), not from card content. The layout measures each card's natural height and converts it to a four-pixel grid-row span including a 16-pixel gap. Cards are assigned round-robin to columns 1, 2, 3, then each new card starts immediately after the previous card **in its own column**. This preserves the first row's left-to-right sequence and keeps each column in source order without leaving row-wide holes.

The prerendered HTML cannot know card heights. Before client measurement, desktop scripting-enabled browsers show up to 18 token-based skeleton cards (bounded by the result count) over the still-measurable grid; the unfinished row-grid is hidden, then all positioned cards appear together. Several rows fill the visible loading area instead of leaving a blank second row. The skeleton is not data and is hidden from assistive technology. Mobile keeps its final single-column layout from first paint, while no-script desktop retains visible, usable cards rather than a permanent loading state. Do not replace this with another client-only masonry library: it would still lack server-side measurements and reintroduce the flash.

True masonry cannot also guarantee strict row-by-row visual rank order when card heights differ: a later card in a shorter column can start above an earlier card in a taller column. Source and keyboard order remain unchanged; rank labels make the intended ordering explicit. On narrow screens, cards use one-column document flow. The desktop layout records each measured height as an intrinsic-size fallback before enabling offscreen `content-visibility`, so skipped cards keep their space during scrolling and theme changes.

## Project evidence

GitHub cards show title, summary, source repository / language, recorded stars / forks, and tags when available. Separate title, summary, source, metrics, and tags with a consistent 12px vertical rhythm; changing row spacing must not squeeze the title/action columns or the summary width. Keep stars and forks in one non-wrapping flex row; their variable-width numbers do not need fixed grid columns. Open-issue counts are neither persisted nor shown: without context, the number is not a useful quality signal. Global star rank uses the existing subdued outlined number badge before the title, replacing the redundant GitHub mark; it is not a second star count or the current filtered-list position. The top-right corner stays reserved for Save, and long titles wrap beside the badge rather than moving it to a separate line. Counts and sort keys come from `sourceMeta`; never substitute invented values. Peer cards keep the same type roles and metadata order even when summaries have unequal lengths.

Cards with a recorded GitHub star count strictly above 1,000 keep the existing Card as the interactive content inside the official React Bits `StarBorder` component. The upstream demo uses two fading horizontal sweeps; on a much larger card with a one-pixel edge, those gradients appear as intermittent flashes. The site adapter keeps the component and its two decorative layers but replaces their path with two continuously rotating, opposite conic highlights at the demo's five-second cycle. This is a card-specific adaptation, not a claim that upstream already traces all four sides. The one-pixel wrapper uses site `border` and `ring` tokens and owns the single visible border, while the inner Card keeps its content and action layout without a duplicate ring. The adapter also removes the upstream demo padding, colors, and 20px radius in favor of the site's 8px card radius. Reduced-motion visitors get the static token border. The threshold follows refreshed `sourceMeta.stars`, not rank or an invented score.

An ordinary click on a card or list row opens the single shared project preview and changes the address to its stable `/projects/:owner/:repo` URL. The stretched title anchor itself points to that internal URL, so modified clicks, JavaScript-disabled browsing, copied links, and direct requests reach a prerendered standalone detail page. The original GitHub URL is a separate explicit action. Preview and standalone page share one content component and show only stored facts: title, repo identifier, summary, category, language, available star/fork counts, optional pinned review-source link, and tags. Neither fetches a third-party README. Make the summary the main reading block; counts are compact evidence, not a three-column dashboard. Do not repeat the rank badge.

The preview has a dim backdrop and one restrained surface. Project and news dialogs share a header component: the title's own line height owns the first row and its top inset matches its left inset; the save and close controls are positioned over that row and centered to it, never increasing the row height or pushing the title down. Source metadata spans a separate full-width row and cannot shift the controls. The shared footer gives the outbound action equal top and bottom padding at the same responsive inset as the header; enlarging its bottom space must enlarge its top space, not move the button off-center. A narrow dialog scrolls its content without covering it with the header or outbound action. The GitHub action is explicitly labeled. Opening either project or news preview navigates with TanStack `resetScroll: false`, preserving the scrolled directory beneath Base UI's body scroll lock. Base UI owns outside-press dismissal; do not add a second backdrop click handler, because that consumes two history entries. Backdrop click, Escape, Close, and browser Back dismiss the preview and restore the prior directory URL/filter and scroll position; browser Forward reopens the masked preview, while refresh turns the public project URL into its standalone page. Focus returns to the triggering card or row.

## Boundaries and checks

Only recorded URLs and remote media belong to their sources. Do not invent entries, tweet IDs, screenshots, or claims. Do not add analytics, remote icon kits, or an unrelated visual theme. Keep the full JSON and generated README available for audit without making them the first-read UI.

Verify both view modes, filtering, empty search, modified-click fallback, preview dismissal and focus return, desktop and narrow reflow, and light/dark parity. Check the real rendered page rather than assuming that a build alone validates composition.
